# 旧项目只读复查与选中后执行

## 确认对象与当前状态

用项目索引、当前聊天或明确路径定位真实根，先核对 AGENTS、README、manifest、已有进度与必要源码。Git 项目查看根、分支与工作区状态；非 Git 项目以核实的实际目录为准。仅因路径有项目名不表示仓库或代码仍存在。

只读阶段允许读取源码、静态分析和已知安全的检查；不跑会改文件、下载依赖、迁移数据库、访问生产服务或产生费用的未知脚本。需要运行测试时先检查脚本行为，在隔离临时目录进行必要检查，区分静态发现和实测结果。没有执行就写“未运行”。

需要复查多个项目时，先浅读再选择最有价值的少数，结合上次复查时间轮换。用户指定项目时优先用户目标，不为轮换而切换对象。云端仅 README 可读时只给与该证据相称的建议，不冒充完整代码审计。

## 形成有证据的机会

每项机会包含：
- 类型：已确认问题 / 待核查问题 / 优化假设 / 扩展机会。
- 证据：当前文件绝对路径与行号、仓库固定位置、相关日志或实际测试输出；不要仅复述旧聊天结论。
- 用户收益与适合现在处理的原因。
- 最小修改范围、依赖条件与可能影响。
- 可重复的验证方法与尚未验证部分。

“没有看到测试”只证明本次查看范围没发现测试，不断言整个项目没有测试。“源码看起来可能失败”通常是待核查问题；能从明确控制流证明的缺陷可标静态确认，但不能称已复现。性能优化先提出基线和指标，未测量不承诺提升比例。

以本次会话真实选择的模型重新审查。模型身份不可知就记录 unknown，不从宣传、工具名字或猜测声称已换新模型。换模型只是审查条件，不是修复或优化证据。

## 执行转换

默认行为是建议，绝不因为某项排名第一就动手。用户明确要求实现/修复/优化一个已确定目标时：
1. 确认所选报告条目与真实项目，重新检查当前状态和适用规则；已有执行授权无需再次询问。
2. 将建议收敛为具体修改目标与验收。若“做第3个”可能对应多份报告或多个目录，只澄清这一处。
3. 保留用户已有改动；必要时用宿主工作区隔离机制。Git 项目不擅自 stash/reset/提交；非 Git 项目用明确的可回滚副本保护受影响文件，不复制密钥。
4. 仅修改所选项目和必要文件，用与目标相称的检查验证；将“已修复”“测试通过”“性能提升”分别绑定真实证据。
5. 在技能状态记录该推荐已进入实施以及验证结果。项目内部稳定知识仅在已确认项目根的已有权威记录中更新，不把跨项目个人画像写入项目规则。

选择实施不自动授权推送、发布、发送通知、支付或改其他项目。若后续步骤已有用户明确授权，遵循现有授权继续，不设置仪式化审批。

收尾写明改了什么、为什么、实际验证、未验证事项及结果位置；若只是复查，明确本次没有修改项目。
